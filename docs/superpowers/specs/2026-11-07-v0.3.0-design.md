1. Anyone can deploy their own Anchor instance with the **Deploy to Cloudflare** button
   (<https://developers.cloudflare.com/workers/platform/deploy-buttons/>).

   developers quickly.

## Requirements

### Deploy button

- The button deploys the repository root, not a subdirectory. Cloudflare reads the Wrangler config at the
  root, and a subdirectory deploy requires a fully isolated app; the Worker needs `apps/web/dist`
  and `@anchor/shared`.
- `wrangler.jsonc` lives at the root:
  - `main: apps/server/src/index.ts`;
  - assets from `apps/web/dist`;
  - migrations from `apps/server/migrations`.
- The D1 binding `DB` has no `database_id`. The button provisions it. Wrangler ≥ 4.45 provisions
  bindings that have no ID, and manual deployers add the ID that `wrangler d1 create` prints.
- Root `package.json`:
  - `build` builds the dashboard.
  - `deploy` is `wrangler d1 migrations apply DB --remote && wrangler deploy`. It has no `pnpm`
    inside, because Workers Builds may run it through npm.
  - `wrangler` is a root devDependency.
  - Humans keep `pnpm deploy:worker`; `pnpm deploy` is a pnpm built-in.
- The setup page asks for one secret. The root `.dev.vars.example` lists exactly `ANCHOR_ROOT_KEY`.
  Root `package.json` `cloudflare.bindings.ANCHOR_ROOT_KEY.description` says to generate the value
  with `openssl rand -base64 32` and to back it up offline first.

### First-owner setup without a token

Supersedes the setup-token rule in `2026-11-06-anchor-design.md` (§ Auth, "Setup").

- `POST /api/v1/setup` takes `{ email, name, password }` and needs no token. It works only while
  there are zero users; the insert is atomic, so concurrent submissions create exactly one owner and
  every other request gets `409 conflict`. A request after setup never changes the existing owner.
- A body that still carries `setupToken` (older clients, scripts) is accepted and the field ignored.
- `ANCHOR_SETUP_TOKEN` is no longer read. A deployment that still has it set keeps working; the docs
  say it can be deleted.
- Accepted risk: until the owner exists, anyone who reaches the URL can create it. The docs say to
  open `/setup` right after the deploy finishes, and how to recover if someone else got there first
  (nothing of the deployer's is stored yet: delete the database's users, or the database, and
  redeploy). Setup stays audited (`auth.setup`, with IP).
- Tests prove the failure cases: a second setup is refused and the owner unchanged, a concurrent
  pair yields one owner, invalid input creates no user.
- The README states the **Workers Paid** requirement next to the button. Password hashing exceeds
  the Free plan's CPU limit.
- A clone made by the button is an independent repository. Upgrading means merging the upstream
  tag and pushing; Workers Builds then migrates and deploys.
- Existing manual installs must move their `database_id` (and local `.dev.vars`) to the root on
  upgrade. The CHANGELOG and the upgrade guide say so.

### Docs

  - Option A is the button. Option B is manual, with every command run from the repo root.
  - Both create the first owner through `/setup`; curl remains an alternative.
- **Upgrade guide:**

  - removes the stale `v0.1.0` example;

### Dashboard

- **Pointer cursor:**
  - a base style gives `cursor: pointer` to enabled buttons and to ARIA buttons, menu items,
    options, tabs, checkboxes and switches, `select`, `summary` and `label[for]`;
  - disabled elements get `not-allowed`;
  - no `cursor-default` in dashboard source; the token lint enforces this.
- **No `·`:**
  - the token lint rejects U+00B7 in dashboard source;
  - the environment page header becomes a breadcrumb: project name, a chevron, then the environment
    name;
  - other uses become words or layout.
- **Tables:**
  - Rows have one height. The secret comment moves to its own **Comment** column, truncated with
    the full text in a tooltip.
  - Folder rows are one line, without the duplicated path.
  - Narrow columns (Version, Updated) get fixed widths.
  - Overview check icons are vertically centered with the key.
  - Footer counts are singular for 1 ("1 token").
  - The audit **Target** column shows the `metadata.name`/`metadata.email` when present instead of
    a raw ID.
- **Motion:**
  - row hover color transitions;
  - newly mounted body rows fade in;
  - hover-revealed actions fade;
  - dialogs, sheets, dropdowns, popovers, selects and tooltips animate both in and out (150–200 ms);
  - a global `prefers-reduced-motion: reduce` rule removes animation and transition time.

### README media

- **A reproducible pipeline:**
  - a Playwright config `apps/web/playwright.media.config.ts` starts a fresh local instance, seeds
    fake demo data through the public API, and writes PNGs to `docs/media/`;
  - `docs/media/cli.tape` records `docs/media/cli.gif` with `vhs` against the same instance.
- **README layout:**
  1. tagline;
  2. the button and the Workers Paid note;
  3. hero screenshot;
  4. a three-line CLI install;
  5. the GIF;
  6. a 2×2 feature gallery;
  7. then the existing sections.
- **Demo data is fake:**
  - no token-shaped string, which the repository test enforces;
  - no one-time token reveal in any shot;
  - the CLI recording stores credentials in a temporary file store, never in the user's keychain.

## Non-goals

- A hosted demo instance.
- Automatic upgrades for button clones.
- Secrets Store bindings.
- Any server or API change, beyond reading audit metadata that the UI already receives.
